④ 仙人たちの3本の軸

Hermesが「これだけは外すな」と返してきた、AI Web制作の3本の軸。これがおけ森の次のHP案件の指針になる。

軸①：Visual Regression ＋ 顔検出を「実装ループ内」に常駐

実装が終わってからQAするんじゃない。実装している最中に、毎回スクショ差分＋顔被り判定が走る状態にする。

→ 道具：Playwright + Percy / Chromatic / BackstopJS、face-api.js / MediaPipe Face Detection

今日のかいさんHPに当てはめると：ヒーロースライダー生成後にPlaywrightで自動撮影→顔検出で「口元被り」を即検知。私の24パターンQAは見落としてた領域。

軸②：Content / Presentation 完全分離を物理的に強制

「原文を変えるな」を ルールに頼らず、構造に頼る。コンテンツをJSON / MDXでデザインと別レイヤーに置けば、AIが触れる範囲が物理的に制限される。

→ 道具：headless CMS（Sanity / Contentful / Strapi）、JSON content、kernel.mdの強制参照プロンプト

今日のかいさんHPに当てはめると：原文をJSON化してデザイン層と完全に分離。AIは presentation 層しか触れない構造に。

軸③：本番反映は「管理画面ZIP禁止」・WP-CLI / Git Deploy必須

今日の32MB詰まり。世界はもう、WP管理画面でZIPアップロードしてない。

→ 道具：WP-CLI（wp plugin install）、GitHub Actions deploy、rclone / lftp、Headless WordPress + Vercel/Netlify

今日のかいさんHPに当てはめると：プラグインはWP-CLIでインストール→Git Deployで本番反映。AI単独・ファイル選択15秒も要らない世界。

├── 06_IMAGE_CONSTRAINT.md    # AI画像事前判定（アスペクト比・被写体数）
├── 07_CONTENT_SEPARATION.md  # 原文保護構造（JSON / MDX分離）
├── 08_FAILURE_DB.md          # ハマり所蓄積（再発防止）
└── 09_QA_GATE.md             # 納品前チェックリスト

そしてこの順番で進める制作フロー：

  1. 参考サイト分解（00_KERNEL → 01_REFERENCE_ANALYSIS）

⑦ ⚠️ でもね、油断禁物だにゃ

ここからが大事。Hermesの返り、骨格は最高だった。でも、そのまま鵜呑みにすると、また別の穴に落ちる。

  • Vercel偏重：返答にVercelブログ引用が多い。Vercelエコシステム強いのは確かだけど、おけ森はWordPress組み込み中心。Vercel AI Gateway Plugin等は実在検証が必要。
  • 具体URLの存在検証必要：「2026-05-20公開」みたいな具体URL、本当に存在するか後でWebFetchで確認すべき。Grok-4はweb検索するけど、要約過程でURLが微妙にズレることがある。
  • 実装コード例は薄い：「Playwright + 顔検出」「WP-CLI + Git Deploy」と言われても、具体コード例レベルの詳細はあまり返ってきてない。着工する時は論点1個ずつ深掘りリサーチが要る。
  • これは「見取り図」：いきなり実装に走らない。各論点を Codex MCP で個別深掘り → 検証 → 実装 の三段。

⑧ 用語解説

難しい言葉をやさしく言うと

Visual Regression Testing（ビジュアル回帰テスト）
一言で言うと：「前のスクショと今のスクショを並べて、何ピクセル違うか機械が見てくれる」自動チェック。
おけ森で言うと：かいさんHPのスライダー、修正前と修正後で「あれ、ここ崩れてない？」を人間の目じゃなく機械が拾ってくれる。
気をつけること：差分があっても「意図した修正」を機械は判別できない。人間が「これはOK差分」を承認する運用がセット。
WP-CLI
一言で言うと：WordPressをコマンドで操作する公式ツール。
おけ森で言うと：wp plugin install ./pukari.zip --activate 一発で、管理画面の「ファイルを選択」も「アップロード」も「有効化ボタン」も飛ばせる。今日の32MB詰まり、これで終わる。
気をつけること：サーバーにSSH接続できることが前提。レンタルサーバーによっては使えないことも。
Headless CMS
一言で言うと：「コンテンツの倉庫」と「見た目」を完全に分けて作る考え方。
おけ森で言うと：甲斐さんの原文は別の倉庫にJSONで置いて、HPはそれを「読みに行く」だけ。AIは見た目しか触れないから、原文を勝手にアレンジできない。
気をつけること：WordPress組み込み案件にいきなり頭から導入は重い。次のHP案件以降から徐々に。
State × Layer Matrix
一言で言うと：「スライダーの状態1・状態2・状態3 × CSS共通レイヤー・個別レイヤー」を表にして、どこに何を置くか先に決める設計図。
おけ森で言うと：今日の「2枚目の青緑を共通::afterに置いて1枚目を壊した」事故、これがあれば事前防止できた。実装前に表を埋めるだけ。
気をつけること：「埋める時間がもったいない」と感じても、結局あとで火を消す時間より圧倒的に短い。
GitHub Spec Kit
一言で言うと：「動かす前に仕様を書く」をAIに強制するためのGitHub公式パターン。
おけ森で言うと：「目的→デザイン→実装」の段階で必ず spec.md を作る。今日の引き継ぎ書がもうこの形に近い。
気をつけること：「仕様書を書くだけで使われない」になりがち。読まれる仕掛け（kernel化・物理ゲート）とセット。
